# Logical solution

The final solution extends the existing MVC project and keeps its Client, Trainer and Admin workflows. It does not introduce a second authentication system, scheduler library or separate healthcare appointment table.

| Requirement | Actual implementation |
|---|---|
| Authentication | Program.cs registers ASP.NET Identity for ApplicationUser/IdentityRole and EF stores. AccountController.Register creates only Client membership within a transaction; Login uses SignInManager.PasswordSignInAsync with lockout enabled; Logout is POST. IdentitySeeder creates the four roles and optionally provisions a development admin from user-secrets. |
| Role authorization | AppRoles declares role names. FeaturePolicies.Client, Trainer and Provider are configured in Program.cs. Controller/action attributes are checked on the server. The authenticated fallback policy covers actions unless explicitly anonymous. |
| Dashboards | DashboardController.Client queries own measurements, active plans, notifications and the next approved appointment. Trainer uses PlanAccess for assigned-client data. AdminDashboardData.LoadAsync supplies system-wide admin metrics. HealthcareProfessional routes to Appointments.Index. |
| Workout | TrainerWorkoutsController uses PlanAccess.Workouts/Clients for plan/exercise management. WorkoutsController uses the logged-in client ID for plan/history/log CRUD. WorkoutPlan has per-client dates/status and WorkoutExercise children. WorkoutLog can retain history when an exercise is deleted. |
| Diet | TrainerDietsController manages DietPlan/DietMeal for assigned clients. DietsController stores MealLog only against the logged-in client's eligible plan. Form classes constrain calories, nutrition values, quantities and text. |
| Appointment | AppointmentsController.Book checks future minute-resolution schedule and validates the selected active provider. BookAppointmentForm.Validate rejects both/neither provider. Appointment has nullable TrainerId and HealthcareProfessionalId; the SQL check constraint enforces XOR. Provider ownership is rechecked on every management action; rowversion protects schedule edits. Unique filtered indexes reserve Pending/Approved slots for each provider and client. |
| Healthcare profiles | HealthcareProfessional.UserId is both PK and FK to ApplicationUser. Specialty is stored on the profile; name/email/active status remain on the Identity account. AdminHealthcareProfessionalsController.Create commits account, role and profile together. Edit updates through UserManager and invalidates inactive sessions. |
| Health progress | MeasurementsController validates dates, weight and height, calculates BMI = kg / (cm/100)^2, and stores two-decimal values. ProgressController provides own history or assigned-client history; Summary is admin-only. |
| Reports | ReportService.ClientAsync retains progress, workout, diet and appointment reports and rechecks assignment on every call. AdminAsync retains totals and appends AnalyticsService output. ReportViewModel holds ReportMetric and ReportTable data for Razor/print. |
| Analytics | AnalyticsService.BuildAsync takes a trusted trainer ID from ReportsController or null from the admin report path. LINQ scopes data before aggregate queries. Same-name plans are grouped; distinct ClientId values measure assignments, and log counts measure activity. Monthly counts include first-of-month through today. Most active lists ten clients by monthly workout+meal log count. |
| Reminders | ReminderFilter runs on authorized GET actions in Dashboard, Appointments and Notifications. ReminderService.GenerateAsync uses an isolated scope/transaction and AppointmentClock. It selects the visiting participant's upcoming today/tomorrow Pending/Approved appointments and generates messages for both active participants. Client plan reminders are generated once per local calendar day. |
| Deduplication | ReminderDelivery stores a composite recipient/key primary key. Appointment keys include appointment ID, schedule and today/tomorrow phase; plan keys include type and date. Serializable transactions plus the key prevent concurrent duplicates. Delivery and Notification commit together. A deleted Notification does not delete its delivery record. Deadlock/duplicate races roll back and retry on a later visit. |
| Safe output/errors | Razor encodes output. Global AutoValidateAntiforgeryToken protects unsafe MVC requests; form Tag Helpers generate tokens. SafeExceptionHandler logs internal exceptions and renders a generic page. HTTPS redirection/HSTS and no-store response headers remain enabled. |

## Important boundaries

Appointment provider choice and trainer-client assignment serve different purposes. Clients can request available providers, but a booked consultation does not grant a trainer access to an unassigned client's measurements. HealthcareProfessionals only manage their own appointment records and notifications. Admin analytics are system-wide. Trainer analytics use current active assignments and their own plans/appointments, excluding healthcare consultation details.

Reminders are generated on visits, not at a scheduled background instant. Missed days are not backfilled, and today's appointment reminder is not generated after its time has passed. Changing a schedule can generate a new eligible reminder. Conflicts mean identical date/time slots; no consultation duration/overlap model exists.
