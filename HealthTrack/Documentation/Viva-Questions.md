# HealthTrack viva questions and answers

1. **What is MVC?** Model?View?Controller separates application data, request handling and presentation. Here domain models and form/report ViewModels carry data, Controllers handle actions, and Razor Views render HTML.
2. **Why ASP.NET MVC?** ASP.NET Core MVC gives this C# project typed forms, model validation, Razor rendering, dependency injection, Identity integration and EF Core persistence within one server application. It suits the coursework's role-based forms and reports.
3. **How does authentication work?** AccountController uses SignInManager.PasswordSignInAsync. Identity checks the password hash and issues an authentication cookie; Program validates stamps and active status on later requests.
4. **How does authorization work?** Authorize attributes and FeaturePolicies limit roles, then LINQ ownership/assignment checks limit individual records. Knowing an appointment or measurement ID never grants access.
5. **How are passwords stored?** ASP.NET Identity stores a salted password hash in AspNetUsers.PasswordHash. UserManager handles hashing/verification; application code does not store plaintext or decrypt passwords.
6. **Why ViewModels?** They expose only the fields a form can submit and define validation/display requirements. BookAppointmentForm cannot overwrite ClientId or Status, which the controller determines. ReportViewModel holds presentation metrics/tables.
7. **How does the trainer-client relationship work?** TrainerClient has TrainerId and ClientId FKs, a composite primary key and a unique ClientId index. PlanAccess checks the live relationship, so removal/reassignment immediately changes trainer access.
8. **Can a client book an unassigned trainer?** Yes, booking lists active eligible trainers. Consultation selection is separate from training-plan assignment, and the booking does not grant access to that client's health history.
9. **How is appointment validation implemented?** Required schedule fields, future/time precision checks, active provider lookup, exactly-one-provider validation, owner checks, status rules and rowversion checks operate in the server. Unique filtered indexes handle racing slot reservations.
10. **How are healthcare appointments represented?** The same Appointment table has nullable TrainerId and HealthcareProfessionalId. A check constraint requires exactly one. HealthcareProfessional links one-to-one to ApplicationUser and stores Specialty. Existing trainer appointments retain their original TrainerId.
11. **What can a healthcare professional access?** Their own appointments and notifications. Provider actions allow approval, future rescheduling, cancellation and completion after scheduled time. This role has no access to health measurements or trainer reports.
12. **How do reminders work?** ReminderFilter invokes ReminderService on authorized GET visits to Dashboard/Appointments/Notifications. Upcoming today/tomorrow appointments notify both participants; date-active workout/diet plans notify the client once daily. No timer or external scheduler runs.
13. **How are duplicates prevented?** ReminderDelivery uses recipient plus deterministic key as a unique primary key. A serializable transaction commits the ledger and Notification together. Reading/deleting a notification cannot reset delivery. Rescheduling changes the appointment slot key.
14. **What if nobody opens the site?** No reminder is generated until a relevant visit. Past-day messages are not backfilled and a passed appointment time does not create a today reminder. A future improvement is a durable background delivery process.
15. **How is BMI calculated?** WeightKg divided by HeightCm/100 squared, rounded to two decimals in MeasurementsController. Positive/range validation prevents zero-height division. The project stores the calculated value per measurement.
16. **How are analytics generated?** AnalyticsService scopes EF LINQ queries by role, groups same-name plans, counts distinct assigned clients and log entries, and computes monthly engagement. Admin sees all data; trainer sees current active assignments and their own plans/appointments.
17. **What is appointment completion rate?** Completed appointments divided by all appointments in the report scope, multiplied by 100. Pending, approved and cancelled are in the denominator. Empty scope displays zero with a no-appointments explanation.
18. **What is an active client or plan?** Active client means an enabled Client account in the report scope, not proof of a recent login. An analytics/reminder active plan has Active status and a date range covering today. Most Active Clients is ranked by monthly workout plus meal log entries.
19. **Why group plan names?** This database stores one plan row per client, not shared plan templates. Grouping names allows similar assigned routines to be compared without restructuring completed plan features. Names are not globally unique routine identifiers.
20. **How does EF Core work here?** ApplicationDbContext maps entities/relationships to SQL Server; LINQ is translated into parameterized SQL and SaveChanges persists tracked changes. AsNoTracking is used for many read-only queries.
21. **What are migrations?** Versioned Up/Down schema changes generated from the model. The two coursework migrations add healthcare provider support and the reminder ledger; migrations are applied explicitly before startup. The snapshot records the final model.
22. **How do you preserve existing records?** The provider migration makes TrainerId nullable without rewriting old trainer rows. Restrict FKs/history-aware deletion prevent accidental removal of dependent records. Optional exercise references use SetNull to preserve logs.
23. **How is security handled beyond roles?** Antiforgery tokens, bounded validated inputs, dedicated form models, encoded Razor output, parameterized EF queries, active-account/stamp checks, lockout, generic errors, HTTPS/HSTS and protected secret configuration.
24. **What does rowversion solve?** It detects another request changing an appointment between form load and save. It complements, rather than replaces, unique slot indexes and ownership checks.
25. **How was the project tested?** Refer to Testing.md for actual executed scripts and evidence. Tests exercise temporary Identity accounts, HTTP forms/antiforgery and SQL state, with cleanup. Do not claim visual/mobile or production HTTPS checks unless manually performed.
26. **What would you improve next?** Durable background reminders, optional email delivery, provider availability and consultation duration, paginated report queries, accessibility/browser coverage and stronger account recovery/MFA. These are future work, not implemented coursework claims.
